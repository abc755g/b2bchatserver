# Подключение к внешнему порталу или сервису

Сценарий: у вас есть свой сервер по этому инсталлятору, и внешний сервис (партнёрский
портал, корпоративная платформа) предлагает интеграцию — общие комнаты, вход сотрудников
через него, синхронизацию контактов. Что сервис делает у себя — его дело; здесь только то,
что для этого нужно на вашей стороне.

Инсталлятор не привязан к сервису: все адреса, токены и названия ниже вам даёт тот, к кому
вы подключаетесь. Единственное исключение — B2B-портал (b2b-links.ru), для которого
инсталлятор и написан: его адреса известны заранее и предлагаются на установке, но в
конфиг попадают только с вашего согласия.

## Коротко: B2B-портал

| Что | Значение |
|---|---|
| Matrix-сервер портала | `chat.b2b-links.ru` — предлагается в блоке «Федерация» при установке; позже `./manage.sh federation --add chat.b2b-links.ru` |
| Подтверждение домена | в портале: раздел «Настройки сервера Matrix» → токен; у себя: `./manage.sh verify-domain --token <ТОКЕН>` или TXT-запись |
| Вход сотрудников | OAuth 2.0 через ваш MAS (пункт 3), без настройки; без MAS — код от бота портала в личку |
| Политики портала (пункт 5) | не нужны: изоляция вашей компании — граница вашего сервера |

Домен, на котором сотрудник открывает сам портал (`portal.b2b-links.ru` или домен
дилера), на вашу настройку не влияет: whitelist федерации — это список Matrix-серверов,
а не сайтов. Браузер с любого домена ходит к вашему серверу напрямую по Client-Server
API, и CORS для этого Synapse и MAS отдают сами.

## 1. Федерация с сервером сервиса

У сервиса есть свой Matrix-сервер. Его домен добавляется в ваш whitelist, после чего
общие комнаты и личные сообщения между вашими и его пользователями начинают ходить:

```bash
./manage.sh federation --add <домен-сервера-сервиса>
./manage.sh federation --test <домен-сервера-сервиса>
```

Если сервис публикует список своих серверов по ссылке — `--sync-from <url>`, см.
[federation.md](federation.md). Со своей стороны сервис добавит ваш домен у себя; пока
этого не произошло, тест покажет, что ваш сервер снаружи виден, а его — не отвечает.

## 2. Подтверждение владения доменом

Прежде чем связать ваш сервер с аккаунтами своих пользователей, сервис обычно просит
доказать, что домен ваш. Два стандартных способа; какой из них поддерживает сервис —
скажет он сам.

**TXT-запись в DNS.** В панели регистратора домена добавьте запись, которую выдал
сервис. Ничего на сервере менять не нужно; распространение DNS занимает до часа.

**Файл по адресу `/.well-known/`.** Сервис выдаёт токен, вы публикуете его:

```bash
./manage.sh verify-domain --token <ТОКЕН>
```

Токен становится доступен по `https://<ваш-домен>/.well-known/b2b-matrix-verify` — это
путь, который проверяет B2B-портал. Другой сервис может ждать файл под своим именем —
тогда `--path <имя-файла>`. Команда сама проверяет, что токен читается снаружи. После
подтверждения файл можно оставить — он ничего не раскрывает.

## 3. Вход ваших сотрудников в сервис

Сервису нужно понять, что сотрудник, который к нему пришёл, — это действительно
`@ivanov:<ваш-домен>`. Пароль от вашего сервера он не спрашивает никогда; вместо этого
сотрудник входит **на вашем сервере**, а тот подтверждает сервису, кто это.

Это штатный вход клиента Matrix по OAuth 2.0 (спецификация Matrix v1.15+), тот же, каким
пользуются Element X и Element Web:

1. Сервис находит ваш MAS через `https://<ваш-домен>/_matrix/client/v1/auth_metadata`.
2. Регистрируется у него как приложение — автоматически, со своим названием и
   логотипом (динамическая регистрация клиентов). Ключей или client-id с вашей стороны
   не нужно.
3. Сотрудник видит стандартный экран входа вашего сервера и экран согласия
   «разрешить <сервису> доступ от вашего имени», после чего возвращается в сервис.
4. Сервис получает короткоживущий токен и подтверждает Matrix ID сотрудника у вашего
   сервера. Токен обновляется сам и виден в аккаунте сотрудника
   (`https://<ваш-домен>/account/` → приложения) — его можно отозвать в любой момент,
   как и любую другую сессию.

Что для этого должно быть у вас:

- **MAS включён** (по умолчанию для новых установок). Регистрация приложений разрешена
  политикой MAS: только https, адрес возврата на том же хосте, что и адрес приложения.
  Строка «OAuth для клиентов» в `./manage.sh health` должна быть зелёной.
- **MAS выключен.** У чистого Synapse нет ни OAuth, ни SSO — такой вход невозможен.
  Сервис подтверждает сотрудника иначе — например, присылает код в личное сообщение
  через федерацию (нужен пункт 1; сообщение придёт как приглашение в комнату от бота
  сервиса, код виден после принятия). Это рабочий, но менее удобный путь; если сервис
  его не поддерживает, включите MAS: `./install.sh` → «изменить настройки», затем
  `./manage.sh mas-migrate`.

## 4. Обратный вариант: вход через сервис на ваш сервер

Если наоборот — сервис является для вашей компании источником учётных записей и вы
хотите, чтобы сотрудники входили в ваш чат его логином, — сервис выступает
OIDC-провайдером для вашего MAS:

```bash
./manage.sh oidc --issuer <issuer-url-сервиса> --client-id <client-id> --name "<Название>"
```

Команда напечатает `redirect_uri` — его нужно сообщить сервису. Локальный вход по паролю
остаётся, так что администратор не потеряет доступ, если сервис недоступен.

Учтите: Matrix ID неизменяем. Аккаунт, созданный через провайдера, навсегда остаётся
привязан к тому, что провайдер прислал как `preferred_username`. Если у сотрудников уже
есть аккаунты на вашем сервере, сначала обсудите с сервисом, как их сопоставить, и только
потом включайте вход.

## 5. Политики доступа от внешнего сервиса

Некоторые сервисы не только федерируются, но и предлагают централизованные правила: кто
кого может пригласить, кто кого видит в поиске людей, можно ли включить шифрование в
общей комнате. Технически это модуль `synapse-http-antispam` — он уже стоит в образе
Synapse этого инсталлятора и по каждому такому действию спрашивает внешний сервис по
HTTP. Без настройки модуль выключен.

Включается блоком в `config/synapse/homeserver.yaml` (адрес, токен и список колбэков
выдаёт сервис):

```yaml
modules:
  - module: synapse_http_antispam.HTTPAntispam
    config:
      base_url: https://<адрес-который-выдал-сервис>
      authorization: "<токен>"
      do_ping: true
      enabled_callbacks:
        - user_may_invite
        - user_may_join_room
        - check_username_for_spam
```

После правки — `./manage.sh restart --service synapse`. Важно понимать, что вы отдаёте:
при недоступности сервиса модуль **запрещает** перечисленные действия (создание комнат,
приглашения, вход), а логин и чтение истории продолжают работать. Включайте только те
колбэки, которые сервис явно перечислил, — лишний закроет соответствующую операцию.

## 6. Совместимость версий

Внешние интеграции опираются на конкретные возможности Synapse и MAS. Минимум для
сценариев выше — версии, запиненные в этом инсталляторе (`IMG_*` в начале `start.sh`):
Synapse `v1.159.0`, MAS `1.23.0`. Если сервис требует иную версию, он должен сказать это
явно; обновление — правка пина и повторный `./install.sh`, см. README.

## Что сервис не получает

- Доступ к вашему серверу, базе или медиа — нет и не требуется.
- Пароли ваших пользователей — вход всегда на вашей стороне.
- Комнаты, которые не связаны с ним федерацией, — whitelist ограничивает трафик только
  его сервером.
